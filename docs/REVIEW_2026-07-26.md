## Bugs

All five are confirmed. B1–B4 have probe output; B5 is a direct code-path reading with no
counter-evidence.

### B1 — `redis-in` SUBSCRIBE/PSUBSCRIBE failure is silently swallowed, node reports green

`redis.js:576` and `redis.js:595`:

```js
client[node.command](node.topic, (err, count) => {});
```

The error argument is discarded. Nothing is logged, no status changes, and the initial status
set by `attachStatusListeners` stays green because the socket itself is healthy.

Probe — an ACL user with `-subscribe`, then a `redis-in` node in `subscribe` mode:

```
>>> SUBSCRIBE denied by ACL: node.error = [] node.warn = []
>>> node.status last call = { fill: "green", shape: "dot", text: "connected" }
```

The node will never receive a message and presents as healthy. Any subscribe-time failure
behaves the same way: ACL denial, an invalid channel, a subscriber-mode restriction.

Secondary: this is the only callback-style ioredis call left in the runtime, which CLAUDE.md
bans outright ("never add callback-style ioredis calls").

**Impact:** high. Silent data loss with a green light is the worst failure shape for an
operator.

### B2 — stored-script `SCRIPT LOAD` failure never reaches the log

`redis.js:989-996`:

```js
const loadScript = async function () {
  try {
    node.sha1 = await client.script("load", node.func);
    node.status({ fill: "green", shape: "dot", text: "script loaded" });
  } catch (err) {
    node.status({ fill: "red", shape: "dot", text: "script not loaded" });
  }
};
```

The catch sets a red status but drops `err`. Its Function-mode twin, `loadLibrary` at
`redis.js:985`, does call `node.error(err)` — the asymmetry looks unintentional.

Probe — `stored: true` with `func = "this is not ( valid lua"`:

```
>>> node.error calls after bad SCRIPT LOAD: 0 []
```

The Lua compile error is invisible. Every subsequent message then falls back to `EVAL` and
fails with the same compile error, so the flow does surface _an_ error eventually — but the
root cause, at deploy time, is never shown.

**Impact:** medium. Recoverable, but diagnosis is much harder than it needs to be.

### B3 — Lua sends a phantom empty `ARGV` when Keys=0 and `msg.payload` is absent

`redis.js:1044`:

```js
const argsWith = (head) => [head, node.keyval].concat(msg.payload);
```

`[].concat(undefined)` appends one element rather than none, and ioredis stringifies
`undefined` to `""`. So a keyless script invoked with no payload receives one empty argument.

Probe — `keyval: 0`, script `return #ARGV`, `msg` with no `payload`:

```
>>> #ARGV with undefined payload = 1 (expected 0)
```

Any script branching on `#ARGV == 0` takes the wrong path.

**Impact:** medium. Silently wrong, and the failure surfaces inside user Lua where it is hard
to trace back to the node.

### B4 — non-array object payload is silently coerced to `"[object Object]"`

Same line. `keyval > 0` is guarded at `redis.js:1038` ("Payload is not Array"); `keyval === 0`
has no guard, so an object payload passes through JavaScript string coercion.

Probe — `keyval: 0`, script `return {#ARGV, ARGV[1]}`, `msg.payload = {a:1}`:

```
>>> [#ARGV, ARGV[1]] with {a:1} = [1,"[object Object]"]
```

**Impact:** medium. See decision D-1 — the fix direction is a judgement call, not obvious.

### B5 — blocking-input status never clears after recovery

`redis.js:627` (xreadgroup) and `redis.js:676` (blpop/brpop/bzpop) reset `attempt = 0` on a
successful iteration but leave the yellow `retrying` status in place.
`attachStatusListeners` only reacts to socket events (`ready`/`close`/`reconnecting`/`end`),
and a recovery that never dropped the socket fires none of them.

Realistic path: a consumer group does not exist → NOGROUP warning + yellow `retrying` → the
operator runs `XGROUP CREATE` → messages start flowing normally → the node still reads
`retrying` for the rest of its life.

**Impact:** low-medium. No data loss, but the status becomes untrustworthy, which undermines
the value of every other status in the package.

## Performance

### P1 — cluster stored-scripts load on one master only

`redis.js:991` calls `client.script("load", node.func)`, which ioredis Cluster routes to a
single node. The Function-mode path at `redis.js:942-949` already does this correctly:

```js
const targets = typeof client.nodes === "function" ? client.nodes("master") : [client];
```

Consequence: in cluster mode, every message whose key routes to a shard other than the one
that received the `SCRIPT LOAD` pays a `NOSCRIPT` round-trip plus a full script-body resend.
It is functionally correct — that is exactly the "Lua fallback" the cluster spec asserts — so
this is a throughput cost, not a defect.

### P2 — static `Params` re-parsed on every message

`redis.js:876` runs `JSON.parse(node.params)` per message when `msg.payload` is absent, even
though `node.params` is immutable node configuration. Parse once in the constructor and store
the result (keeping the current "invalid JSON → `done(err)`" behavior, just moved).

## Stability

### S1 — unthrottled error logging on pooled clients

`redis.js:1158`:

```js
connections[id].on("error", (e) => {
  config.error(e, null);
});
```

ioredis's default `retryStrategy` retries forever with a capped delay, so an unreachable host
produces one Node-RED error log entry per retry attempt, indefinitely. There is no dedupe,
throttle, or backoff on the logging itself.

Arguably intended (visibility over quiet failure), so this is raised as a question rather
than a defect — see decision D-3.

### S2 — refcount re-arm gap (theoretical, not reachable today)

`redis.js:1162` re-arms the reference count only when it is `undefined`:

```js
if (usedConn[id] === undefined) {
  usedConn[id] = 1;
}
```

but `disconnect` at `redis.js:1213` deletes `usedConn[id]` only while `connections[id]` is
still set. Any path that leaves a stale `0` or negative count behind would cause the _next_
shared client created under that id to start under-counted, and the first close would tear
down a socket other nodes still hold.

**I traced every current call path and could not reach it.** All five constructors call
`getConn` before registering their close handler, so a construction failure leaves both
registries untouched. Recording it because a one-line guard is cheap and the failure mode
(cross-node connection teardown) is severe and very hard to diagnose — not because it is a
live bug.

## Best practices

**C1 — dead code with a documented maintenance tax.** `extractSecrets` at
`redis.js:392-431` is never called at runtime. The only caller is `redis.html:1054`, inside
`oneditsave`, using the editor's own copy at `redis.html:199`. The coverage run confirms zero
executions across the entire suite.

This is 40 lines that CLAUDE.md, `docs/ARCHITECTURE.md:118`, `docs/NODE_GUIDE.md:47-51`, and
source comments in both files all instruct maintainers to keep byte-for-byte in sync with the
editor. Only `mergeSecrets` is genuinely needed at runtime (`redis.js:483`). Deleting the
runtime `extractSecrets` removes the duplication and the sync instruction together.

**C2 — tests violate the repository's own async rule.** CLAUDE.md requires `async`/`await`
"in runtime (`redis.js`) AND tests" and states "Never use `.then()/.catch()` Promise chains".
`redis.js` is clean. The test tree has **58** occurrences across 20 files:

```
23  test/redis_out_spec.js
 7  test/redis_in_spec.js
 6  test/redis_status_spec.js
 3  test/key_commands_spec.js
 2  each: redis_sentinel_deployment, redis_cluster_deployment, memorydb_deployment,
        helpers/cleanup, bit_commands
 1  each: 11 further specs
```

Purely stylistic — no behavior is wrong — but the rule as written is not being enforced, so
either the code or the rule should move.

**C3 — 25 files fail `prettier --check`.** All 9 examples, 8 test specs,
`scripts/run-deployment-tests.js`, `test/helpers/cluster-prone.js`,
`test/playwright/helpers/node-red-editor.js`, and all 8 `docs/superpowers` files.
`redis.js` and `redis.html` are clean. Root cause: `.lintstagedrc` formats only _staged_
files, so anything untouched since the rule was added stays drifted and nothing ever catches
it.

**C4 — pre-commit runs the full Docker matrix.** `.husky/pre-commit` runs `npm test`, which
starts and tears down four Docker deployments (~3 minutes plus container churn) on every
commit. Raised for awareness — CLAUDE.md documents this as deliberate.

**C5 — README links to files not in the package.** `README.md` links to `docs/ARCHITECTURE.md`,
`docs/NODE_GUIDE.md`, and `docs/TESTING.md`, but `package.json` `files` ships only
`docs/assets/readme`. npm's registry page rewrites relative links to the repository so they
resolve there; for anyone reading the README from an installed copy they are dead. Low
priority.

## Test coverage assessment

**Breadth is strong.** 666 runtime assertions across five topologies, a live `COMMAND LIST`
catalog cross-check for the editor datalist, server-side `CLIENT LIST` proofs of connection
pooling, and real-browser editor coverage. Command-family coverage is thorough.

**The gap is depth on failure paths.** Essentially every uncovered line in `redis.js` is an
error, recovery, or shutdown branch. Grouped by value:

### 1. Lua failure and recovery — the largest hole

| Lines       | Untested behavior                                        |
| ----------- | -------------------------------------------------------- |
| `971-972`   | Function mode with no library source → red status        |
| `975-976`   | Function mode with no function name → red status         |
| `982-985`   | `FUNCTION LOAD` failure → red status + `node.error`      |
| `994`       | `SCRIPT LOAD` failure (this is B2)                       |
| `957`       | `inflightLoad` coalescing of concurrent reloads          |
| `945`       | "no Redis master available"                              |
| `1039-1040` | "Payload is not Array" guard                             |
| `1079`      | non-`NOSCRIPT` error rethrow (must NOT trigger recovery) |

`957` and `1079` are the notable ones: the coalescing exists to stop N concurrent messages
issuing N `FUNCTION LOAD`s, and the anchored-prefix check at `redis.js:910` exists to stop a
user script whose own error merely _contains_ "NOSCRIPT" from triggering a re-execution of a
possibly non-idempotent call. Both are deliberate correctness mechanisms with a comment
explaining why, and neither is asserted anywhere.

### 2. Shutdown resilience

`gracefulQuit`'s timeout → forced disconnect (`1186-1189`) and its quit-rejects fallback
(`1194-1197`). `docs/ARCHITECTURE.md:95-107` describes this as one of two shutdown paths, and
the code comment explains the exact scenario it defends against — neither branch is
exercised.

### 3. Connection status transitions

`reconnecting` status (`56`) and the shared-connection "attach while the client is already
reconnecting/ended" branches (`71-75`). `redis_status_spec.js` covers ready and error but not
mid-reconnect attach, which is precisely the shared-connection case
`attachStatusListeners` was written for.

### 4. `redis-in` xreadgroup NOGROUP warning

`656-661` — the exact warning text `docs/TROUBLESHOOTING.md:53-59` tells users to look for.

### 5. `redis-config` test-connection edges

Empty env-var name (`287-289`), a non-`PONG` reply (`338`), `withTimeout` actually firing
(`157`), disconnect-after-failed-test itself failing (`363-366`), and `getConn` client
construction failure (`1167-1168`).

### 6. Redaction — security-adjacent, unasserted

`106-107` (AUTH/HELLO argument redaction) and `122` (`safeStringify` circular fallback). The
test-connection endpoint returns a serialized error and options blob to the editor over HTTP;
`redactValue` is what keeps credentials out of it. Nothing asserts it works.

### 7. Editor JavaScript has no line coverage at all

`redis.html` contains roughly 850 lines of behavior (`syncConnectionToEditor`,

## Decisions needed

Nothing below has been implemented. Each item states my recommendation and why, but the call
is yours.

### D-1 (blocking) — B4: what should a non-array object payload do when Keys=0?

Currently coerced to the literal string `"[object Object]"`, silently.

| Option                      | Trade-off                                                                                                                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Reject with `done(err)`** | Mirrors the existing `keyval > 0` guard. Loudest, matches the node's own precedent. Technically a behavior change.                                                                                  |
| `JSON.stringify` the object | Preserves data, never errors — but invents a serialization contract the help text does not document, and `obj`-style JSON handling elsewhere in the package is opt-in via a checkbox, not implicit. |
| Leave as-is, document only  | Zero behavior change; the footgun stays.                                                                                                                                                            |

**Recommendation: reject.** My reasoning for judging the compatibility risk near zero is that
any flow hitting this today already receives `"[object Object]"` in `ARGV[1]`, which no Lua
script can do anything useful with — so a flow depending on it is already broken. That is an
inference from the data shape, not something I tested against real user flows.

### D-2 (blocking) — which fix scope should I implement?

Test-first per CLAUDE.md, narrowest change per finding.

1. **B1 + B2** — the two silent failures. One `await`/`try`/`catch` and one added
   `node.error(err)`. Highest impact per line changed, and the tests close coverage gaps 1
   and 4.
2. **B3 + B4** — one guard in `argsWith`; needs D-1 first.
3. **B5 + D1 + D2** — clear the stale status; correct the audit note and add `wait.js` to
   both helper lists.
4. **C1 + P1 + P2** — delete dead `extractSecrets`; fan cluster `SCRIPT LOAD` across masters;
   parse `Params` once.

**Recommendation: 1 → 2 → 3, then 4 as a second pass.**

### D-3 — S1: is unthrottled error logging intended?

An unreachable host currently writes a Node-RED error entry per ioredis retry, forever. This
may be deliberate (visibility beats silence). If it should be throttled, that is a design
change to connection error reporting, not a bug fix — I would want explicit sign-off before
touching it, since `docs/ARCHITECTURE.md` treats connection error surfacing as load-bearing.

### D-4 — C2: fix the tests or the rule?

58 `.then()` chains in tests versus a CLAUDE.md rule that forbids them. Rewriting is a large,
purely mechanical diff across 20 files with no behavior change and real review cost.
Narrowing the rule to runtime-only, plus "new tests use async/await", would cost nothing.
**Recommendation: narrow the rule, and convert opportunistically when a spec is edited for
another reason.**

### D-5 — C3: run Prettier across the 25 drifted files?

One mechanical commit, or leave it. Note that `.lintstagedrc` will never catch these on its
own, so without a deliberate pass they stay drifted indefinitely. A `prettier --check` step
in the test runner would prevent recurrence — that is a second, separate decision.

### D-6 — D3: what is the status of the orphaned docs?

`docs/REDIS_8_8_HARDENING_REVIEW.md` still says "changes requested". Options: mark it
resolved/superseded, index it in `REFERENCE_MAP.md`, or move it (and `docs/superpowers/`)
into an explicitly historical location. I do not know which of its requested changes landed;
determining that is a separate piece of work I have not done.

### D-7 — U1/U2: add `engines` and a Node-RED version constraint?

Low risk, and `engines` in particular is standard for a published package. Needs your call on
the actual floor (`>=20`? `>=22`? `>=24`?) since CLAUDE.md names v24 as the _working target_,
which is not necessarily the minimum supported.

### D-8 — dev dependency patch bumps

`lint-staged` 17.1.0→17.2.0, `playwright` 1.61.1→1.62.0, `prettier` 3.9.5→3.9.6. All patch
or minor. A `prettier` bump may reformat files, so it interacts with D-5 — do them in that
order if both are approved.
